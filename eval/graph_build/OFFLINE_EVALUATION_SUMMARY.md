# GraphRAG 离线图谱构建测评与修复总结

最后更新：2026-10-01。测评记录覆盖 2026-09-29 至 2026-10-01。

## 1. 当前结论

本轮主要评估了图谱构建输入、实体与关系抽取、证据支持、实体归一化、图谱投影完整性及基本查询功能。

- **最新 Demo 验收已完成**：文档 56、71、76 的 23 个冻结 Chunk 已使用 v6 重建，经程序校验与 Codex 裁决后，结构 3/3、事实抽查 15/15 SUPPORT、切换后核心查询 3/3 通过；已切换新版，旧版保留。见 [最终验收报告](D:/code/zhiqing-rag-platform/eval/graph_build/rebuild-demo-20261001-v6/README.md)。
- **构建和查询可用**：所检 10 个活动投影全部 READY，3 个直接 Neo4j 查询均返回结果与证据；542 条证据全部可以定位到原文。
- **v3 历史表格回归的低召回改善**：在固定的 13 个表格 Chunk 回归集上，Entity Recall 从 **49.88% 提升到 91.60%**，Relation Recall 从 **43.27% 提升到 87.35%**；本次未复算该集的 v6 分数。
- **已修复的主要问题**：无效候选重试后被空结果掩盖、表格续块缺失真实列头、实体名称自行补词、实体预算偏小及类型识别不清。
- **全库与完整问答验收仍未完成**：最新验收只覆盖上述三文档经裁决后的 Demo 图谱，不代表其他文档、模型原始输出或完整跨文档 GraphRAG 问答已经通过。

这些结论适用于当前 Demo 的构建与排查。测评材料主要是项目中的虚构企业测试文档，不代表真实企业生产文档的整体质量。

## 3. 主要做了哪些测评

| 测评项 | 检查内容 | 已得到的结果 |
| --- | --- | --- |

| Relation Triple Recall | source、relation_type、target、方向及端点类型是否一致 | 最初 40/91；最新回归 214/245 |
| 关系损失拆解 | 两端已抽到时关系是否命中；source/target 漏抽造成多少损失 | 最初 51 条关系未命中均至少缺一个严格匹配端点 |
| 条件、否定与时间检查 | 条件文字是否保留，否定是否被改成肯定，排列是否被误当作流转 | 最初 40 条已命中三元组中，29 条条件文字也严格一致；发现无依据流转和触发条件误建模 |

| Entity Normalization | 应合并未合并、不应合并却误合并、联合角色和材料名称边界 | 已生成身份对候选并确定部分建模口径；正式重复率、误合并率尚无结论 |
| 图谱投影一致性 | 标识、批次/版本、活动投影归属、数量、断边、无证据 Fact、重复与孤立节点 | 所检活动图谱无断边等主要结构异常；发现 30 个全局孤立 Entity |
| Demo 基本功能 | 本地测试、直接 Neo4j 查询和事实小样本抽查 | 最新相关测试 28 项通过；直接查询 3/3 通过；旧图谱事实抽查仍有问题 |

**匹配规则：** 实体采用类型与形式归一化后的名称；关系采用带端点类型的有向三元组。
条件、否定、时间和语义证据需另外检查，三元组命中不自动代表这些属性正确。

“两端已抽到时的关系召回”是端点齐全条件下的指标，不是条件句正确率。
最初该指标为 40/40，但不能据此认为所有关系质量都合格。

## 4. 发现了什么问题，怎么处理

### 4.1 非空候选校验失败后，被空图谱掩盖

**问题：** 对 7 个历史零输出 Chunk 做当前模型隔离复现时，4 个 Chunk 首次实际返回了非空候选。
候选因名称或证据不符合原文校验被拒绝，模型随后返回空图谱，原代码将其视为成功。

**修复：** 增加“非空无效候选之后不能用空结果确认无事实”的保护。继续重试后仍为空，返回
`OUTPUT_EMPTY_AFTER_INVALID`，让任务显式报错；首次合法空结果仍可正常处理。

**效果：** 保存响应的离线回放中，4 个问题 Case 均从静默空成功变成显式错误。
这是防止错误被隐藏的修复，未自动补回漏抽事实。由于缺少历史原始响应，不能将当前复现路径断言为历史零输出的唯一原因。

### 4.2 表格续块缺少真实列头

**问题：** XLSX 开头的稀疏表名或说明被当成列头，续块中的单元格缺少正确列语义。
模型容易混淆事项主题、具体动作、材料和约束。

**修复：** 将表名前言与实际列头分开；每个数据续块重复真实列头；保留原有 512 token 分块上限。

**效果：** 两份试验表的 4 个数据 Chunk 均带真实列头；另 6 份表格的 13 个数据 Chunk 也通过列头与预算检查。
实际模型验证表明，仅修表头仍不充分：4 块使用当时生产提示时命中实体 17/37、关系 2/20；
加入表格语义提示的实验达到 36/37、19/20。后续更广样本仍暴露类型和证据错误，未把这个小样本成绩当作整体质量通过。

### 4.3 实体名称被模型自行补词或改写

**问题：** 原文“变更清单”被改为“核对变更清单”，名词性内容被添加“说明”等动词。
名称不再是当前 Chunk 的连续原文，导致校验失败；即使删掉补词，也可能仍保留错误类型。

**修复：** 重试反馈明确指出错误实体、错误字段、非法名称和对应逐字证据；要求模型重新判断名称与类型。
继续保留严格原文校验，不自动删词后直接接受候选。

**效果：** 同一 13 块回归中，原先 3 个失败 Chunk 全部恢复为非空有效抽取，通过校验的 Chunk 从 **10/13 提升到 13/13**。
名称恢复不等于事实全部正确；后续仍对类型、关系和证据进行排查。

### 4.4 实体数量与输出预算偏小

**问题：** 提示词要求最多 25 个实体、40 条关系，输出预算只有 4096 tokens。
密集责任矩阵的一块有 52 个 Gold 实体目标，25 个实体的提示预算明显不足。
历史表格调用还出现过 `finish_reason=length` 的实际截断。

**修复：** 提示上限提高为 **80 个实体、120 条关系**，与已有 Schema 上限一致；
输出预算改为 **24576 tokens**，并提供 `GRAPH_LLM_MAX_OUTPUT_TOKENS` 配置。
要求逐行检查遗漏，识别有依据但尚未形成关系的实体，不要求凑满上限。

**效果：** 最终 13 块均一次有效返回，无输出截断；同名匹配候选缺失的 Gold 实体目标数从 **167 降到 13**。
预算与类型提示一起修改，因此不能将全部改善单独归因于提高预算。输出增多可能增加模型用量，全量性能尚未测试。

### 4.5 实体类型与业务对象边界不清

**问题：** 字段被当成动作，完成标准被当成状态或材料，检查分类被当成责任角色，采购操作节点被当成 Process。
原文名称即使存在，类型不同也会造成严格实体与关系漏匹配。

**修复：** 在提示中明确 Field、Step、Rule、State、Material、Resource、Actor 和 Process 的区别；
要求结合列头和单元格实际含义判断，不能整列套一种类型。增加通用操作节点示例，
区分单一主责角色的具体 Step 与包含多个操作的 Process。抽取器版本更新为 `graph-extractor-v3`，避免新任务复用旧版本缓存。

**效果：** 名称命中但类型不匹配的目标数从 **36 降到 21**。
中间回归曾出现采购 Step 被判成 Process 的回退；最终轮次该表实体 **72/72**、关系 **60/60** 严格命中。
发布核对表等仍存在类型与边界分歧，未将该问题标记为全部解决。

### 4.6 引文出现，不代表关系受到支持

**问题：** 发现了以下无依据或依据不足的关系：

- 根据状态行排列生成 `TRANSITIONS_TO`，或给并列内容生成 `NEXT_STEP`。
- 把“需要留存的内容”直接解释为某动作 `PRODUCES_MATERIAL` 的结果。
- 把表格范围声明绑定到不对应的材料对象。
- 将暂停、退回触发条件抽成裸 Rule，遗漏其约束效果。

**处理：** 将证据可定位与语义支持分开检查，并保存逐条支持性裁决。
用户确认了材料主名称、分类不作为 Actor、描述不作为动作、不从排序推断流转、保留暂停/退回含义等口径。

**效果与状态：** 在 v2 的 202 条预测关系中，定向人工裁决了 34 条：4 条由完整 Chunk 支持，30 条 INSUFFICIENT；
这 34 条原模型引用片段均不足以独立支持对应关系。它们是挑选疑点的审核，不能推算整体错误率，裁决也不能直接套用到 v3 新输出。
本轮 v3 重点完成预算与类型修复，**尚未完成完整语义关系约束和新输出的 Evidence 验收**。

## 5. 修复后的效果

### 5.1 固定 13 个 Chunk 的同口径对比

使用同一批冻结正文和相同模型配置；Gold 固定为 405 个实体目标、245 个关系目标。
基线、原始响应、提示词、源码和数据哈希均有保存。v3 经 4 轮提示回归后采用最终 r4 结果。

| 对象 | 指标 | v2 基线 | v3 最终结果 |
| --- | --- | ---: | ---: |
| Entity | Precision（保守参考） | 75.94% | **84.13%** |
| Entity | Recall（已标目标） | 202/405 = 49.88% | **371/405 = 91.60%** |
| Entity | F1（同口径参考） | 60.21% | **87.71%** |
| Relation | Precision（保守参考） | 52.48% | **69.93%** |
| Relation | Recall（已标目标） | 106/245 = 43.27% | **214/245 = 87.35%** |
| Relation | F1（同口径参考） | 47.43% | **77.68%** |

Entity Recall 提升 **41.73 个百分点**，Relation Recall 提升 **44.08 个百分点**。

Gold 是看过预测后扩展的、未穷尽的诊断草稿。这批样本也参与了提示修正，结果属于回归验证。
Precision 参考值 = 已知 Gold 匹配数 / 预测数；Recall = 匹配数 / 已标目标数；
F1 参考值 = 2 × 匹配数 /（预测数 + 目标数）。未命中 Gold 的预测仍未决，不自动判为 FP。
因此这里的 Precision/F1 是已知 Gold 匹配的保守参考，不能当作最终全量质量验收分数。

### 5.2 召回损失的变化

| 问题 | v2 基线 | v3 最终结果 |
| --- | ---: | ---: |
| 实体名称未命中目标数 | 167 | **13** |
| 名称命中但类型未命中目标数 | 36 | **21** |
| 实体目标总未命中数 | 203 | **34** |
| 关系因端点缺失未命中数 | 139 | **21** |
| 端点齐全但三元组未命中数 | 0 | **10** |
| 关系目标总未命中数 | 139 | **31** |

最终两端齐全的目标关系从 106 条增至 224 条，其中 214 条三元组命中，即 **214/224 = 95.54%**。
更多端点恢复后，也暴露了 10 条关系类型或方向等严格三元组未命中的情况。
这说明“实体漏抽拖累关系召回”的瓶颈明显缓解，剩余工作包括关系本身及部分端点类型/边界。

## 6. 当前完成到哪一步，Demo 接下来做什么

**已完成：** 输入冻结、Gold 草稿与校验、基线测评、低召回归因、零输出隔离复现、表头与名称反馈修复、
预算与类型修复回归，以及已有图谱的结构和基本查询检查。

**仍未完成：** v3 的完整 Evidence 语义验收、实体误合并/重复率定论、新版本图谱重建及重建后的投影检查。
否定、条件、时间也尚无独立的完整正确率结果，不能只凭分层标签或三元组命中宣告通过。

针对 Demo，建议继续按简单验收推进：

1. 用新版本构建少量代表文档，验证修复是否实际进入图谱。
2. 重点抽查发布核对表、交付物表以及否定、暂停/退回、状态流转关系，处理明确的依据不足事实。
3. 重查投影完整性和带证据的查询，给出这批 Demo 文档的通过/未通过结论。

无需继续要求用户逐条裁决全部预测。本报告整理已有结果，未新增模型调用、数据库写入或图谱重建。
