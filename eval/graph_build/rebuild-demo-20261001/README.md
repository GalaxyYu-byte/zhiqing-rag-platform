## 仍存在的事实问题

1. **遗漏条件**：原文“客户没有立即回复时，处理人仍应保留最后沟通内容和后续联系安排”，预测保留要求但 condition_text 为空，条件性义务被泛化。
2. **规则对象错配**：原文要求“表格用角色或受控标识，不公开列出完整个人资料”，预测把规则绑定到“执行结果”，对象缺乏支持。
3. **属性核对推成字段结构**：原文要求核对“形成时间与确认人”，未明确声明正式文件定义了对应字段，预测直接建立 HAS_FIELD。
4. **可能性说明当成规则**：“多次转派说明分类或责任界定可能存在问题”是解释，预测把它当作“在工单中保留原因”的 GOVERNED_BY 规则对象。

抽查通过的事实包含转派摘要的“影响”“已做排查”等明确字段。
部分通过的规则关系需要完整 Chunk 才能确定对象；短引文只覆盖规则文字，查询时应一并返回完整来源。
没有把两个名称同时出现、证据逐字可定位，自动当作事实受到语义支持。

三个候选再次进行结构校验后，审核门禁均返回 `EVIDENCE_REVIEW_NOT_PASSED`，因此未执行切换。

## 本次修复的构建错误

最初候选 70、71、72 构建失败。真实数据库的冻结触发器禁止更新已发布 Chunk，包括其 metadata；候选缓存原本写入 metadata，触发约束错误。

修复方式：候选缓存改存独立候选任务的 `payload.extraction_cache`，按 Chunk ID、正文哈希、模型和抽取版本核对，不更新已发布 Chunk。
失败候选保留作审计，同一授权范围重新创建 73、74、75，并全部成功构建。
这解决了缓存存储位置的问题，语义抽查中的错误仍需单独处理。

验证：23 项本地测试通过；22 项 SQLite / PostgreSQL 临时表测试通过，包含冻结 Chunk 不被更新的回归。临时表测试不替代完整业务 Schema 或并发压力验证。

文档 76 构建过程中出现一次证据不在原文中的任务错误，重试后成功；最终逐字证据和投影一致性检查通过。
本次覆盖 23 个唯一 Chunk，包含失败和重试调用，不能把它说成总共只调用模型 23 次。
