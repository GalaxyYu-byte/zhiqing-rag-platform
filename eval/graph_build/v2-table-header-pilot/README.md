详见 [实际抽取对比与损失拆解](comparison.md)。以下原有内容记录的是本地列规则试验，不是模型结果。

此目录是**两份 xlsx 的本地重分块试验**，不是已发布数据库中的新批次，也不是完整 59 Chunk Gold v2。来源为冻结 v1 的 `83.xlsx`、`89.xlsx`，输入哈希由 `manifest.json` 绑定；v1 文件没有改动。脚本：`scripts/build_graph_table_header_v2.py build|verify`。

修复后的 `chunking-v2` 将 xlsx 表格开头的稀疏表名/说明与真正列头分开。长表格的每个数据 Chunk 都以实际列头作为 Markdown 表头；表名和说明保存在独立前言 Chunk，避免占用每个数据 Chunk 的 token 预算。当前两份文件从 v1 的 4 个 Chunk 变成此试验集的 **6 个 Chunk**：2 个前言、4 个数据；4 个数据 Chunk 都带第 3 行的真实列头，且每块遵守原配置的 512 token 上限。

离线列抽取在这 4 个数据 Chunk 提议 30 条关系。全部通过当前结构、端点和逐字证据校验，关系证据与两端实体名称都保存在**同一个新 Chunk**。对照原 Gold 的关系名称与方向为 **20/20 严格命中**。这是已参与规则设计的两份测试表格，不能据此估计泛化 Precision；未列入选择性 Gold 的 10 条提议关系也不能直接判错。

另外用未参与规则设计的**合成**运维资料表做了保留测试：不同的资料名称和保管要求、相同的列语义，拆分后的每个数据 Chunk 都有真实列头，12/12 条行内 `Material --GOVERNED_BY--> Rule` 候选的实体与证据在本 Chunk 内。另一个不同列名的合成交接表验证了表头保留和 token 上限；现有列抽取规则对不同列名不会自动产生关系。这些是离线测试，不是实际企业文档上的独立人工证据裁决。

随后又使用 `dox/` 中**未参与规则设计的 6 份 xlsx** 做了留出检查：13/13 个数据 Chunk 保留第 3 行真实列头并遵守 512 token 上限。从其中“采购节点与交接说明”的“主责角色/环节”列，以及“项目交付物核对清单”的“文件或成果/检查要点”列，生成 30 条行内候选；30/30 条的两端名称和引文都在本 Chunk 的同一表格行，且通过端点 Schema 与逐字证据校验。逐条内容及来源哈希见 [unseen-validation](unseen-validation/README.md)。Codex 初步判断列语义支持这些关系，但“文件或成果”中某些名称是否应建为 `Material` 仍需业务裁决。没有独立人工 Gold，故**不能从 30/30 推算 Evidence Precision**。

`manifest.json`、`chunks.jsonl`、`proposals.jsonl` 和 `gold_relation_outcomes.jsonl` 可供复查。未调用 DeepSeek，未写 PostgreSQL 或 Neo4j。现有图谱和原冻结 v1 的 87/165、40/91 基线均未改变。正式采用前还需在真实未见表格上做业务 Evidence 裁决，并为新的 Chunk 边界重新标注 Gold，而不是沿用 v1 的字符偏移。
